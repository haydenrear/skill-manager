VACUITY CHECKS — HIS-11 (#186)

Every assertion this ticket adds, run against the code with its own fix
disabled. An assertion that was not run against broken code is not coverage;
nine assertions in this epic have been caught passing against broken code,
three of them by their own authors.

RUNNER: `jbang RunHis11.java` — CommitPreImageRestoreTest +
CompensationPairingTest + FailureInjectionSweepTest, ~7s. That file IS IN THE
REPOSITORY (repo root), shipped for the reason RunHis12.java is: a record that
names a file which does not exist is a claim, not evidence. Apply the mutation
a V-number names, run it, revert.

The last two suites are in the runner on purpose. They are what a bad
pre-image escrow breaks FIRST — a vacuity sweep that only ever reddens the new
file has not checked that the fix left the existing walk-back contract alone.
They stayed green under every mutation below except where noted.

WHY THIS FIXTURE CAN FAIL AT ALL. #187's case in this same epic is the standing
warning: an empty `previousLock` there made `removeRealization` remove nothing,
so "byte-identical afterwards" was true whether or not anything restored it.
The fixture here has three properties instead:
  (1) the destination is GENUINELY NON-EMPTY before the run — a real unit tree,
      with a nested marker file, digested path by path with SHA-256;
  (2) the incoming tree is GENUINELY DIFFERENT — different SKILL.md body, and
      no marker file — so `deleteRecursive(dst)` in the commit handler has real
      work to do and a delete-only rollback is observably lossy;
  (3) the injected failure lands AFTER the commit, at step 1, so what is under
      test is the walk-back and not the commit handler's own mid-copy
      self-rollback.
Property (1) is checked in the test body as an explicit precondition
(`before.size() >= 3`), and it is NOT the assertion that reddens: the
assertions that redden below are all byte-identity, escrow residue, or lock
behaviour. HIS-4's probe 7a is the standing warning about the other shape — a
probe that reddens only its precondition is not a probe of the claim.

================================================================ V7
THE POST-COMMIT HALT DECISION INVERTED (#233's review, finding #5).
Executor.commit:

  -  if (c instanceof Compensation.RestoreUnitDir r) r.escrow().discard();
  +  if (c instanceof Compensation.RestoreUnitDir r) r.escrow().restore();

  [FAIL] a commit that succeeds keeps the NEW bytes and leaves no escrow behind: the destination holds the newly committed tree: expected <# gamma …
  [FAIL] a HALT after the commit keeps the new bytes and discards the pre-image, deliberately: the committed bytes stay — the halt was about what comes AFTER the commit: expected <# gamma …
  FAILURES: 2

  The point of this one is the SECOND line. `commit` argues in prose that a
  cooperative stop is not a rollback and so a post-commit HALT keeps the new
  bytes; that is the one place an explicitly-argued line in this ticket's new
  code destroys operator bytes, and until now it had no cell. It has one, and
  inverting the decision reddens it.

  The cell's decoder asserts a non-FAILED HALT actually fired, because without
  that it would pass just as well on the ordinary success edge -- i.e. it would
  assert the discard and merely CALL it the halt edge.

  The live instance is on the SYNC path, not the install path: SyncUseCase runs
  CommitUnitsToStore and then BuildInstallPlan, and BuildInstallPlan returns
  okAndHalt when the plan is policy-blocked. #233's review named RunInstallPlan;
  checked, and that handler only ever returns ok or partial, and InstallUseCase
  puts both of its halting effects BEFORE the commit.

================================================================ NOT A VACUITY CHECK
The cell "a commit into an EMPTY destination still rolls back to absent" has no
V-number and is not claimed as one. It is a NON-REGRESSION guard against the
opposite defect — an escrow that restored unconditionally would look correct on
every case above and wrong on a fresh install, resurrecting a unit that was
never there. There is no single-line mutation that reddens it and not V1, so
calling it vacuity-checked would be a claim I did not measure.

================================================================ A NOTE ON THE HARNESS
The first version of the script that applies these mutations reverted them with
`git checkout -- <path>`. That restores to HEAD, not to the state the mutation
was applied on top of, and it silently discarded uncommitted work TWICE during
this ticket -- once for the whole of the original Executor change, once for the
drain. Nothing was lost (both were reapplied and re-verified before anything was
pushed), but the shape is worth writing down for whoever does mutation testing
next: snapshot the file CONTENT in memory and write it back, and commit before
you start. A revert mechanism that consults a different source of truth than the
thing it is reverting is its own small version of this epic's recurring defect.
