HIS-14 — vacuity checks
=======================

Every assertion in HomeBindsBothAxesTest, disabled-fix-first. Each block names
what was disabled, and pastes the VERBATIM failure the suite printed. Run with
`jbang RunTests.java` under a scratch $HOME (see probes/his-14/README.md for the
runner), so no check could reach the operator's real agent homes.

The known traps this pass had to survive, from the ticket:
  (a) a probe that reddens only a PRECONDITION is not a probe of the claim;
  (b) a fixture whose ambient environment already names the target home cannot
      detect an unbound axis.
Both bit, and both are recorded below as findings rather than elided.

TRAP (b) FIRED HERE, TWICE, AND BOTH ARE FIXES TO THE FIXTURE:

  1. `the printed env prefix is a RENDERING of the binding` derives its expected
     string FROM `AgentHomes.binding`. With the binding shrunk to one variable
     both sides shrink together and the containment still holds — the assertion
     passes against a product that binds half. It is the explicit
     `assertEquals(4, binding.size())` that reddens, and that line exists only
     because this check was run. Without it the case would have been vacuous in
     exactly the way this epic keeps finding.

  2. `the printed remedy RUNS` PASSED on its first V2 run. Its shell removed
     CLAUDE_CONFIG_DIR / CODEX_HOME / GEMINI_HOME, and with all four unset the
     agent axis falls back to the STORE axis — so a binding that pinned only
     SKILL_MANAGER_HOME still landed everything in the right place. The fixture
     now EXPORTS the three agent variables naming the other home, which is both
     the discriminating case and the case an operator is actually in.

TRAP (a) ALSO FIRED, in the first V2 run: the shell case reddened on
`the other home has content to be damaged (3 entries)` — its own floor guard,
not the claim, because the other home was three empty directories. The fixture
now builds a POPULATED other home (a store plus the three config files the real
damage edited), and the same run then reddens on the claim itself.

FLOOR — the case that is deliberately not a claim
-------------------------------------------------
`FLOOR: a projection into a home's agent dirs is observable` passes under every
V above, and that is correct: it exists so that "nothing appeared in the other
home" cannot pass by nothing having happened anywhere. It is a probe of the
FIXTURE, and it is labelled that way rather than counted as evidence.

The same role is played inside `otherHomeIsUntouched`, which refuses a
before-snapshot with fewer than six entries — the mechanised form of trap (a),
since an empty snapshot makes every later comparison trivially true.

V8 — the FROZEN gate alone removed
----------------------------------
**THIS ONE FOUND A DEFECT IN THE FIXTURE, NOT IN THE PRODUCT, AND IT IS THE
REASON THE FROZEN HALF HAS A PROBE AT ALL.**

The HIGH-2 case is frozen AND read-shaped, so it reddens if EITHER gate is
removed and proves neither on its own. V8 removed only the frozen gate and
got:

  [FAIL] a WRITING verb does not reconcile a FROZEN home either:
         not true: a frozen home is not reconciled, whoever asked: rc=127
         migrated installed-unit record: legacy-probe.json

— the product doing exactly what the new case says it must not. Except the
case was RIGHT and the fixture was wrong: both frozen fixtures wrote
`policy.toml` by hand, and the file is `home.policy.toml`. Neither home was
ever frozen. The read-only gate returns first, so the earlier case passed on
the OTHER gate and looked like evidence for both.

A fixture that states a precondition through a string literal is a fixture
that can be wrong about it. Both now go through `HomePolicy.write` and assert
`HomePolicy.load(...).frozen()` as an explicit precondition. Re-run against
the corrected fixture, V8 reddens on the claim:

  [FAIL] a WRITING verb does not reconcile a FROZEN home either
  [FAIL] the printed remedy RUNS, in a shell whose environment names another home
   → 15 passed, 2 failed


MED-4 — the suite no longer depends on the shell
------------------------------------------------
In the first round `runtests.sh` passed `env -u CLAUDE_CONFIG_DIR …` and the
suite went 9/1 without it:

  [FAIL] an ambient CLAUDE_HOME naming another home does not survive the binding:
         precondition: an ambient CLAUDE_HOME decides the config dir:
         expected <…/other/.claude> but was <…/his14b/fake/.claude>

Trap (a) — reddening on a PRECONDITION — inside the file written to close
trap (b). The case is about the CLAUDE_CONFIG_DIR-UNSET branch of the
precedence, and `setOverride` could say "this variable is X" and "stop
overriding this variable" but not "this variable is not set", so the
assertion silently depended on the developer's shell.

`AgentHomes.setUnset` is the third state. With it, measured both ways on the
same tree:

  CLAUDE_CONFIG_DIR / CODEX_HOME / GEMINI_HOME / SKILL_MANAGER_HOME unset
      HomeBindsBothAxesTest  → 17 passed, 0 failed;  whole suite ALL PASSED
  all four EXPORTED, naming a scratch home
      HomeBindsBothAxesTest  → 17 passed, 0 failed;  19 pre-existing failures
      elsewhere (AgentHomesTest, HomeDescriptorTest, LauncherShimsTest, the
      #145 test) — the same 19, in the same suites, as on the BASE commit
      before any of this ticket's code. Filed as DEF-042; they are the same
      "cannot say unset" gap, and `setUnset` is the fix they need.
