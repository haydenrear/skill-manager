LOCAL SIGNAL — "an edit to a skill inside a worktree home changes what that
home's shim runs."

Three homes. The wrapper is installed ONCE, in A, and then copied to B exactly
as a clone, a child home, or a `cp -a` would copy it. Nothing is reinstalled at
any point below.

  the shim installed in A, run from A : I am the copy in home A
  the SAME shim, standing in B        : I am the copy in home B

  now EDIT the skill inside B and re-run B's shim — nothing reinstalled:
    B's shim                          : I am the copy in home B, EDITED
    A's shim, unaffected              : I am the copy in home A

  and the sanctioned fallback: a home with NO copy, symlinked from A
    C's shim                          : I am the copy in home A

  the wrapper's bytes name no home at all:
    rel="plugins/skt/src/skt/cli.py"
    home="$(cd -- "$shim_dir/../.." && pwd -P)"
    exec "$py" "$entrypoint" "$@"

Before this change the second line read "I am the copy in home A", the edit in
B changed nothing an agent could observe through the CLI, and C behaved
identically to B — which is the point: the frozen shim gave the RIGHT answer in
the one home that happened to have installed it, and the wrong one everywhere
else, with a local copy sitting unused.

The rule is "prefer this home's copy, FALL BACK to the pinned one", not "always
this home", so C is a pass and not a failure: C holds no copy of skt, and
reaching the home it was pinned to is what the second clause is for. The pin is
FOLLOWED (through the shim's own symlink) rather than STORED, because a stored
absolute path would also be taken by B — which has its own copy — and that is
the defect again.

DEFERRED FINDINGS — what HBR-1 did with the two it inherited

DEF-HBR-002 (HomeCloner.sanctionedParentShim sanctions on shape alone):
  NOT TAKEN. Left deferred, deliberately, and the reason is not timidity.

  It is a change to what `home verify` and `home repair` REFUSE, and the 16
  pairs it would start refusing were not written by any generator this ticket
  fixed -- they are parent-shaped symlinks laid down by home materialisation,
  which no installer contract reaches. Turning the gate on now would convert a
  latent defect into a hard failure for every already-standing home on the
  machine, days before HBR-5 measures the goal, and the two graphs this ticket
  is required to keep green (checkout-home, project-child-home) are exactly the
  ones that build parent/child shim pairs. Moving the gate and fixing the
  generators in one PR would also make the goal unreadable: HBR-5 could not
  tell which of the two produced the number.

  The metric is decided by HBR-5's own walker, not by `home verify`, so leaving
  the gate where it is costs the goal nothing measurable. What it costs is that
  `home verify` still exits 0 on those 16 pairs, which is DEF-HBR-002 exactly,
  and it stays open with HBR-5 as its owner.

DEF-HBR-001 (skill-dev-skill's installer delegates to `uv tool install`):
  NOT TAKEN, and it is genuinely not an installer edit. The frozen bytes are
  uv's console-script wrapper, so the fix is either "make a uv tool install
  relocatable" or "post-process what uv writes" -- a design question, needing
  uv and a network to even reproduce, which is why HBR-0's sweep records it as
  uncovered rather than skipping it silently. Unchanged, still open.
